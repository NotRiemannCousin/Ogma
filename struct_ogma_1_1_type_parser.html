Template Parameters
Tis the type that will be parsed.
ArgDefinitionis the annotation that describes the given option (like in [[ =Ogma::Arg{ "numbers" } ]]).

They are the mandatory arguments that needs to be presented, but every function has a Annotations template pack that can carry the remaining annotations of the option, so it's possible to specialize their behaviour based in other annotations (like [[ =Ogma::Arg{ "config" }, =Ogma::mustExist, =Ogma::fileOnly ]]).

ExpectedFlags

ExpectedFlags is a function that returns every possible flag than can match with this option (without the "--" prefix). When you compile a program with "g++ main.cpp -o main.exe -freflection -std=c++26", "-o", "-freflection" and "-std=c++26" are flags used to select some behaviour.

In Ogma every option can be specified by multiple different flags, but normally you will need just { "", ArgDefinition.longName } (see Positional vs Named Arguments to know how the empty flag works).

Parse

Parse is responsible to the actual parsing of the arguments. It has the flag used to match with this option (if applicable), just like "--cool-flag" or "--use-match".

The curr field is the old living object passed by value to Parse (you can move it to Parse). It exists because a argument can pass through Parse multiple times. Things like the std::chrono classes or numerics types just ignores the old value, but containers can append values when called multiple times (they can also discard the old values. For consistency, if you need to specify this relation of conditional append/override you can use Ogma::Overwrite or Ogma::Append).

Notably, in the example from the last paragraph -std=c++26 sets not only the flag but also the value it takes, so Parse receives both the flag matched and the remaining args to set the value.

Spec

Spec is the third contract point. It never affects parsing, it exists only so the help page can show what the parser actually accepts. The member parameter carries the reflection of the data member being documented, this way a specialisation can derive semantic metavars with things like std::meta::identifier_of, or tell a declared default apart from a value-initialised field with std::meta::has_default_member_initializer. Filling it is the one place where a specialisation is allowed to be lazy, the fallback composes every field from ArgDefinition and the member identifier.

The full extension contract is documented in TypeParser structure.

behaviour

This is the fallback behaviour of TypeParser. For any T with no specialisation of its own, it will act as a struct-walking engine towards all Ogma eligible members (with Arg or VariantArg), handling positional and named flag.

Delegates to details_::DefaultSpec, so a member shows the ArgDefinition flag, a comma separated list of every flag it answers to, and a metavariable derived from its own identifier.
