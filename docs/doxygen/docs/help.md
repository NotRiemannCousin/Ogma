# Help

Ogma generates every help page from the same annotations that drive parsing. There is no help text written by hand
anywhere, no registration step, and no way for the page and the parser to drift apart, they are two readers of the
same declaration.

## Where it comes from

For each scope, the engine builds a page from three sources. The member's own `TypeParser::Spec` provides how the
value is consumed (flag spellings, metavariables, modifiers). The `Arg` annotation provides the prose. The
structural walk provides the grouping, what is positional in this scope, what is named-only, whether there is a
subcommand dispatch.

`--help` answers at every scope. It shows the page of the scope you are in, `app --help` shows the root,
`app compress --help` shows the branch. The help scope path grows as you descend, a branch opened by `compress`
inside `filetool` shows `Usage: filetool compress ...`.

## The usage grammar

The usage line has four kinds of fragments, and the delimiters are the whole vocabulary.

- a bare fragment, required with fixed position
- `(fragment)`, required with free position, order does not matter
- `[fragment]`, omittable, only ever an `std::optional`
- `<COMMAND>`, the subcommand dispatch

A positional member shows its flag in the usage line on purpose. A flag-filled member leaves the positional queue,
so `a b c` and `--file x a b c` do not map to the same slots, and a bare-metavar usage would promise a one-to-one
positional mapping that mixing flags breaks.

When a scope declares more than five optional fragments, the optional group collapses into `[OPTIONS]`. The required
group never collapses.

## Sections

The page is divided by what a member IS, not by which face of it is being shown.

- **Commands**, the declared subcommand cases, with their descriptions.
- **Positional arguments**, members that answer to bare tokens. Each row also documents the member's named face,
  since a flag-filled member leaves the queue and the named form is otherwise undiscoverable.
- **Named options**, members that only answer to flags. This section is hidden when the scope declares none.
- **Other**, the automatic entries. `--help` is always there, `--version` is there when the root declares
  `AppInfo`, and the closing token `-` is documented as an entry too.

`--help` and `--version` are reserved spellings. No member can claim them, and the reservation is a compile-time
error, so the page can advertise them unconditionally.

## Modifiers

Modifiers are appended to a member's own description, and each one is generated by the member's type parser, never
free text. `[format: hex]` from `hexNumber`, `[format: binary]` from `binNumber`, `[format: SI]` from `siNumber`
and `siFloat`, `[range: 0..100]` from `Range`, `[must exist]`, `[file]` and `[dir]` from the filesystem annotations,
`[format: human time]` from `durationFmt`, `[format: unix seconds]` and friends from the time point formats,
`[allow infinity]` from `allowSpecialValues`.

For enums the metavars list every accepted name, bar-separated, enumerator identifiers followed by their aliases.
The list obeys the enum's case sensitivity. With `caseInsensitive`, spellings the parser would fold together appear
once.

## Errors carry the scope

Error messages chain from the outside in, one context prefix per scope crossed. The leaf owns the "what"
(`invalid number: 'abc'`), the engine owns the "where" (`serve`, `--retries`). Missing required members are reported
together, one line each, and a missing subcommand lists every accepted case.

## Plain text only

The returned page is plain text, with no ANSI escapes, newline terminated. It is safe to pipe, diff and parse.
Styling, if you want any, happens at the printing boundary, on your side of the library.

## The programmatic API

`Ogma::HelpText<T>(scopePath)` renders the page of any scope without parsing anything, and the interception
guarantees it equals what `--help` would serve for the same scope. If you want to print help from your own code, or
write your own `main` loop, this is the entry point.
