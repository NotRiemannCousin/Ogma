◆ Parse()

template<class T>
Result< T > Ogma::Parse ( ArgSpan args)

Named options are matched by flag spelling. Every member's own TypeParser::ExpectedFlags (minus the positional "" entry) feeds a constexpr flag table, and a "--"-shaped token is looked up there. Members that accept a positional invocation are parsed in declaration order, a bare token fills the first still-unfilled positional entry, and a VariantArg member matches the subcommand names declared in its cases. Both paths go through the same per-member setter, so repeated named occurrences keep accumulating (or overwriting) exactly as each member's own parser decides, and a member reached positionally cannot be claimed twice.

A plain Arg annotated member whose own type is itself an unspecialized struct with Arg/VariantArg members recurses automatically. There is no separate dispatch for it, it simply reaches TypeParser<FieldT>::Parse like any other member, and that type's primary (unspecialized) fallback IS the same struct-walking engine used at every level, root or nested alike. Such a member is entered through one of its own ExpectedFlags spellings (or, when its type is positional-capable, directly by a bare token), after which its own flags and positional members are recognised in place. An explicit closing token (Ogma::closingToken) ends that nested member's own token stream and hands the remainder back to its caller.

Any input left over once T is fully parsed, including a stray, unconsumed closing token, is reported as an error.

A "--help" token is intercepted by the scope that sees it (and "--version" too, when the root declares AppInfo), which aborts parsing by throwing HelpRequested carrying the rendered page. Catch it if you drive Parse directly, or use ParseAndExecute which already handles it.

The token-level rules (positional queue, named table, subcommand dispatch) are documented in Positional vs Named Arguments, and the nesting rules in Scopes.

◆ closingToken

std::string_view Ogma::closingToken { "-" }
constexpr

The scope-based counterpart of the POSIX end-of-options delimiter: instead of ending option parsing globally, it exits exactly one level of nesting — a container, a nested structural member or an opened subcommand — and hands the remaining arguments back to the parent scope. It is optional whenever the argument list ends there anyway, and a trailing one at the root is harmless.

◆ controlToken

std::string_view Ogma::controlToken { "--" }
constexpr

In POSIX it terminates option parsing; here it "opts out" of the next token being read as a flag instead — a value that merely looks like one. In containers it opens a new element of named-only values; in positional strings it lets a value carry flag-shaped content, as in "-- &ndash;base64=idk" . It is not an end-of-options delimiter: parsing of the surrounding scope continues normally after it.
